# KPF-62 G3 acquisition and prospective MuSiQue alternate

The B7 audit of October 21 found that its original progress logs had truncated objectives and lacked chunk identities, full prompts, and task gold. Its reported corpus index was already retired; those audit records cannot reconstruct the desired token-level corpus. `g3_b7_acquire.py` accepts a future export only when the original self-hashed RTE record includes an affirmative layout match **and full prompt SHA-256**, independently retained prompt bytes reproduce it, logged chunk spans and hashes match, and an independently supplied task-gold record joins by task ID. The existing RTE layout only has 12-character chunk hashes and does not provide that full-prompt digest. The tool refuses it; it does not retroactively create a measurement warrant, assert source authenticity from hashes alone, tokenize data, or qualify a G3 gate. Producers must supply original record and prompt binding at capture time, under applicable privacy policy. Input JSONL: `--records` original complete self-hashed producer objects; `--captures` objects `{record_sha256,prompt}`; `--gold` objects `{task_id,target}`; `--out` a new path. Its output contains only IDs, full hashes and observed span coordinates, not prompt or answer text.

A usable **prospective alternate**, not B7 traffic, comes from the retained ZeroSCROLLS MuSiQue test JSONL. `g3_musique_acquire.py` selects unmodified original requests and gold whose original paragraphs recur at different offsets or predecessor histories. It records original source line, full source/line/prompt/target hashes and character spans; it caps selection at the first 16 qualifying paragraphs and never manufactures a question, answer or chunk. `g3_musique_tokenize.py` then invokes the provided `g3_vocab_tokenize.cpp` helper, loading the actual GGUF **vocabulary only**, and discards spans that fail exact token-prefix boundary checks. It rechecks token-level chunk recurrence and calls `g3_manifest.inspect` rather than claiming readiness. The output is a *proposed short-stratum workload*, not approved B7 data, not a production prompt manifest, and not a quality or model result. The existing exact-token-match task scorer is a literal-answer diagnostic; its validity for these free-text answers has not been established. No threshold or metric was changed.

Build and invocation (examples use the fully linked experimental candidate; verify source/binary and library identities for any other build):

```sh
c++ -std=c++17 -O2 -Iinclude -Iggml/include -Ivendor scripts/chunk-kv/g3_vocab_tokenize.cpp \
  -L "$CANDIDATE_BIN" -Wl,-rpath,"$CANDIDATE_BIN" -lllama -o "$VOCAB_HELPER"
python3 scripts/chunk-kv/g3_musique_acquire.py --source "$SOURCE_JSONL" --out "$SELECTION"
python3 scripts/chunk-kv/g3_musique_tokenize.py --source "$SOURCE_JSONL" --selection "$SELECTION" \
  --model "$MODEL_GGUF" --model-header-bytes 10996704 --tokenizer "$VOCAB_HELPER" \
  --lib-dir "$CANDIDATE_BIN" --out "$NEW_OUTPUT_DIR"
```

`--model-header-bytes` is the reported GGUF data offset for this exact model header, not a general constant for other models. Run vocabulary work under a CPU/RAM claim; no model inference is performed. Verify the report's tokenizer and mapped library custody on the eventual run host. The helper disables automatic special-token insertion and special-token parsing, making the tokenization policy explicit; these unrendered source prompts still need the role's production chat-template decision before a serving claim.
